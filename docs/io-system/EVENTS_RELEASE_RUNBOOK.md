## Authority and data boundary

Forward migrations: `20261002201815_secure_community_event_discovery_and_registration.sql`, then `20261002224602_public_event_guest_registration.sql`. Public guest details are specified in [EVENT_GUEST_REGISTRATION_RUNBOOK.md](EVENT_GUEST_REGISTRATION_RUNBOOK.md).

- Public guest registration is the default for new events. Name/email proof uses a private credential link and the shared capacity engine; hosts can choose Community/chapter restrictions. Original active membership remains required for hosting and Community-only registration. Existing event restrictions remain until reviewed.
- Anonymous callers cannot select the raw `events` table. `discover_events` supplies a bounded public projection with no private address/join URL or guest identities. Public events appear in discovery; unlisted events require an explicit ID; members-only invitations enforce active membership even for a direct link. Search/date/format/offset/limit are checked server-side.
- Existing `location`/`link` fields are copied into `private.event_access_details`, then cleared from public rows. Existing addresses are not automatically republished as a “city”. Operators must review public description content, which can contain whatever a host deliberately writes.
- Browser INSERT/UPDATE/DELETE of events and legacy RSVP writes are revoked. Existing legacy RSVP records are retained; Going/Interested history is not silently converted into confirmed registrations. The obsolete browser RSVP module is removed. Chapter submission delegates to the same trusted event submission API.
- The caller is derived from Auth and checked against the expected account in the same transaction as each end-user mutation. New hosts submit pending events; supplying an approved status is ignored. Explicit approved hosts can publish general events. Chapter publication additionally requires active chapter lead authority; otherwise it needs review. Event approval never silently approves the host's future publication.
- Content operators need database-owned `content.manage` capability, a non-suspended identity and AAL2. Missing AAL fails closed. A separate operator reviews their host approval. Eligible chapter leads can review another person's chapter submission. A trigger also protects status changes through the pre-existing admin content RPC. Event rejection uses the actual `declined` state.
- Submission IDs bind to a caller and content fingerprint. Replays create one event; changed content cannot reuse an ID. Title/description, future start/end, maximum duration, timezone, HTTPS access links, cover, capacity and scope are checked by the database.
- Registration requires completed Community onboarding and no active suspension. Default scope is active **Indus Orbit membership**, with an explicit chapter-only option. The owner subsequently asked for the nearest Luma adaptation. Official Luma documentation permits ordinary guest registration by name/email without platform membership, with calendar-membership restrictions on selected tickets. A specific question about changing the earlier membership requirement is pending; the implemented gate remains restricted until that is resolved. Chapter-only registration checks active chapter membership at the server.
- Registrations have separate confirmed, pending, waitlisted, cancelled and rejected states. Event-row locking serializes registrations, cancellations, host decisions and check-in. Pending requests reserve no place. Capacity limits confirmations; cancellation promotes the oldest approved, still-eligible waitlisted guest. Rejected guests cannot silently re-register.
- Only a current eligible confirmed guest or authorized host/operator receives private access details. Cancellation/suspension withdraws further guest access. Guest lists expose names/status/check-in only to authorized hosts/operators, using server pages of at most 100; no email export or marketing permission is implied. Host check-in is idempotent and limited to eligible confirmed guests within the event's operating window.
- Account/event changes destroy prior private UI state. Focus/visibility and a five-minute visible-page interval revalidate private access without reloading the invitation. Private details are withheld while that check is unresolved. A failed check does not leave the previous credentials or guest list as authorized data.

New private tables have RLS enabled and no anonymous/authenticated raw grants. Privileged RPCs have empty search paths and explicit role ACLs. The two deliberate public projection RPCs are narrowly granted to anonymous/authenticated roles; private tables/helpers are not public projections.
